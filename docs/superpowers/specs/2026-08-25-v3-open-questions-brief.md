# GPCompaRe V3: open questions brief

Written 2026-08-25 for an outside reviewer with no prior context. Everything needed to
give useful advice is here. The constraints in section 3 are the ones that make most
generic advice unusable, so read them before answering.

---

## 1. What the thing is

**GPCompaRe database** is a static website publishing a structural-bioinformatics dataset:
residue-residue contact score (RRCS) changes between active and inactive predicted
conformations, for all 283 human Class A GPCRs.

For each receptor the pipeline compares two AlphaFold-multistate models, scores how strongly
each pair of residues is in contact in each state, and reports the difference (ΔRRCS) per
contact pair. Colour convention throughout: **red = stronger in the active state, blue =
stronger in the inactive state.**

The site is generated by a Python + Jinja2 script and deployed as plain HTML to GitHub Pages.
No server, no framework, no build step, no npm. Four page types:

- **Landing** with search, headline counts, and top-5 receptor cards
- **Browse**, all 283 in a sortable, filterable table
- **Statistics**, 10 cross-receptor charts including a "Core Functional Residues" analysis
- **Report** x283, each with an interactive snake plot (GPCRdb-style topology diagram), five
  tables, four charts, and a methods section

It is owned by a small academic lab. Its audience is people arriving from the lab's
forthcoming paper: reviewers and readers who need to understand it, trust it, and cite it.

## 2. Where the work stands

V2 is live. A V3 branch is built but unmerged and undeployed. V3 deliberately did **not**
redesign the site. It added, on report pages: a sticky section nav; a "Compact view" toggle
that folds the page's nine sections; deep links that encode the snake plot's view and filters
in the URL hash so a paper can cite a specific view; and an opt-in "analysis layer" adding a
key-number strip, a per-receptor segment fingerprint, and CFR badges on existing table rows.
On the landing page it added an explainer teaching what RRCS is.

The engineering is verified: 26 tests, a mechanical test proving approved report content is
byte-identical with the new features off, and four rounds of adversarial review that removed
six separate statements the underlying data did not support.

**The landing-page explainer is the part that failed.** See section 4.

## 3. Hard constraints

Advice that violates these is unusable. They are not preferences.

1. **The 283 report pages were approved by the lab's PI and their content cannot change.**
   The rule V3 was built under: the default view of an approved page is exactly what the PI
   signed off; anything new is opt-in, off by default, and remembered per reader. A test
   enforces it.
2. **No generated prose on report pages.** 283 auto-written sentences are 283 places for a
   referee to object. Non-prose devices only: numbers, badges, layout, charts.
3. **No overclaiming, at all.** This is the lab's strongest stated preference and it has
   already bitten repeatedly. Every rendered sentence must be supported by what the pipeline
   actually computes. See section 5 for the specific traps.
4. **No new toolchain.** Python + Jinja2 + hand-written CSS and vanilla JS. Introducing
   npm, a bundler, or a JS framework is explicitly rejected: the site is mostly finished and
   needs better explanation, not better ergonomics.
5. **Display name and URL deliberately disagree.** The brand is "GPCompaRe database"; every
   URL and host stays at the legacy lowercase `gpcompreports`. This is intentional so existing
   links and citations keep working. Do not propose "fixing" it.
6. **No em dashes in user-facing copy.**

## 4. The open questions

### 4a. The landing-page explainer needs rethinking (primary question)

The current explainer is a schematic: two grey circles labelled "A" and "B", a bond drawn
thin in the inactive state and thick red in the active state, with invented values
"RRCS 0.4", "RRCS 2.9", "ΔRRCS +2.5".

The owner's verdict: it "looks like nothing in the report or the paper." That is the right
criticism. The schematic teaches the concept in a visual vocabulary the reader never meets
again. Every other surface on this site speaks in snake plots, real GPCRdb generic numbers
(`6.48x48`), and named receptors.

**Question:** how should a landing page teach RRCS to a first-time reader using the site's
real artifacts rather than an invented diagram? Candidate directions, none settled:

- A real snake plot fragment from a real receptor, coloured by real ΔRRCS
- A single real contact pair, with its real numbers and real GPCRdb numbering, shown as it
  appears in a report table
- A worked example that walks one receptor from structure to number to page
- Something that mirrors a figure from the paper, so the site and the paper share a visual
  language

Relevant: the paper is family-wide Class A plus a PAR2 case study, so PAR2 is the natural
worked example and is already the most examined receptor in the project.

### 4b. Two new pages

- **Contact page.** New. What belongs on it for an academic resource: lab, corresponding
  author, how to report a data error, how to ask for a receptor?
- **Downloads page.** Already scoped but unbuilt. It will eventually offer a downloadable
  local copy of the software, plus the dataset. Open: what to ship (the batch CSVs as-is, a
  curated release archive, the generator itself?), how to version it, and whether a DOI via
  Zenodo is worth the per-release process.

### 4c. The wider question

The site was scoped as a "paper companion": optimise for a reader arriving from the
manuscript. Adding a contact page and a software download nudges it toward being a
maintained community tool, which implies versioning, support expectations, and a
maintenance burden a small lab may not want. **Is that drift intentional, and if so what
else does it commit the lab to?**

## 5. Data traps that break naive advice

All verified on disk, all non-obvious:

- **Annotation coverage is uneven.** The fraction of above-threshold contact endpoints that
  map to a named structural segment ranges from 45.9% to 100% across receptors, median 84%.
  Any cross-receptor comparison that ignores this is biased. One receptor has 65% coverage
  and looked systematically "enriched" until the base was corrected.
- **The single largest change in a receptor is usually an artifact.** The biggest ΔRRCS
  typically sits in a flexible terminus or loop where the structure prediction is least
  reliable. Anything reporting "the largest change" must restrict to structured regions or
  flag the rest.
- **GPCRdb numbering lives in a column named `display_number`.** The column named
  `generic_number` exists in all 283 files and is empty in every one.
- **Two different "top N" definitions for the same concept coexist.** The Statistics page
  publishes a Top 30 CFR list; other code paths use 50. A badge citing rank 43 sent readers
  to a page that did not list it. Now unified on 30.
- **One report section is titled "Complete RRCS results" but is capped at 1000 rows**, so it
  is incomplete for 7 of 283 receptors. Pre-existing, still unfixed.

## 6. What a good answer looks like

Concrete and opinionated. Name a direction and say why the alternatives lose. Assume the
constraints in section 3 are immovable and the traps in section 5 are real. If a proposal
needs new content on a report page, say so explicitly, because that requires going back to
the PI and is the most expensive thing anyone can ask for here.
